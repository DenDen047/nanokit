TL;DR

全面置き換えは不可、「レビュー系 = 公式プラグイン / 対話・検索系 = 既存 MCP」の役割分担が現実解。 公式プラグインは MCP ではなく Codex app server を直接叩く別経路で、threadId を使った継続対話の仕組みを持たない。 そのため codex-discuss・ultrasurvey 検索レッグが依存する codex mcp-server の登録は存続が必須。 一方、両経路とも同じ ~/.codex/config.toml と認証を継承するので「最高モデルの単一ソース」原則はそのまま保たれる。

推奨: プラグインを導入して自作 /codex-review をレビュー用途で置き換える（バックグラウンド実行と公式メンテが主な利得）。 /codex-discuss はそのまま残す。/lgtm-loop は threadId 継続レビューに依存する唯一の難所で、当面は現状の MCP 経路を維持し、プラグイン試用後に再設計を判断する（論点 3）。 Stop フックの review gate は暴走リスクがあるため OFF のまま使わない（論点 4）。

1. 公式プラグインの中身

openai/codex-plugin-cc（OpenAI 公式、v1.0.6、28k stars）は Claude Code のプラグイン形式で、スラッシュコマンド 8 個 + サブエージェント 1 個 + 補助スキル 3 個 + フック 3 種を提供する。

コマンド役割備考（出典: README）
/codex:review未コミット変更 or ブランチ diff のレビュー読み取り専用。--background / --wait / --base <ref>。カスタム観点の指定は不可
/codex:adversarial-review設計判断・前提を攻めるレビュー唯一 focus テキストを渡せる（steerable）。読み取り専用
/codex:rescueタスク委譲（調査・修正の実行）--model / --effort / --resume / --background。書き込みあり
/codex:transferClaude セッションを Codex スレッドに変換codex resume <session-id> で Codex 側で続行できる
/codex:status /codex:result /codex:cancelバックグラウンドジョブ管理result は Codex セッション ID も返す
/codex:setupインストール確認・review gate の ON/OFFgate は既定 OFF のオプトイン

実装機構（統合判断に効く事実）

  • MCP ではない。 Node スクリプト（codex-companion.mjs）が Codex app server を叩く。mcp__codex__* ツールは提供されない。
  • ローカルの codex バイナリと認証・設定をそのまま使う（README「Codex Integration」）。 ~/.codex/config.toml と、trusted プロジェクトではプロジェクト直下の .codex/config.toml を継承する。
  • コマンドはすべて disable-model-invocation: true （例: commands/review.md）。 つまりユーザーが明示的に打ったときだけ動き、自然文から自動発火しない。
  • フックは 3 種（hooks.json）: SessionStart / SessionEnd（各 timeout 5 秒、ジョブ台帳の管理）と Stop（timeout 900 秒、review gate 用。gate 無効時は素通り）。
  • レビュー出力は JSON スキーマで構造化 （review-output.schema.json）。 severity は critical / high / medium / low の 4 段階で、自作 codex-review の CRITICAL〜LOW と互換。
  • 要件: Node ≥ 18.18（手元は v22.22.3）と codex バイナリ（手元は 0.144.1、/codex:setup が適合性を検証する）。

4. 論点 1〜7

論点 1: codex mcp-server の登録を廃止できるか → できない

プラグインは MCP ツールを提供しないので、廃止すると codex-discuss・ultrasurvey 検索レッグが全滅する。 さらに headless 文脈（task-radar の実行レッグ等、claude -p で回る仕事）ではスラッシュコマンドより MCP ツールの方が扱いやすい。

結論: MCP 登録は無条件で存続。「統合」は置き換えではなく二経路の役割分担として設計する。

論点 2: 自作 /codex-review を置き換えるか → 置き換え推奨

最大の利得はバックグラウンド実行。現在の MCP 呼び出しは同期的で、大きな diff のレビュー中ターンが塞がる。 プラグインは --background + /codex:status / /codex:result でこれを解消し、 レビュー中に別作業を続けられる。また Codex 側のレビュー機能改善（モデル更新・プロンプト改良）に公式が追従してくれるため、 これまで手動でやってきたモデル名更新コミット（例: a92b31d「Codex review now on GPT 5.6 Sol Max」）が不要になる。

失うものは 2 つ。(1) 日本語カスタム観点プロンプト — ただし観点を指定したいケースは /codex:adversarial-review の focus テキストで代替できる。 (2) 出力末尾の threadId 契約 — これは lgtm-loop だけが使うので、論点 3 と一体で扱う。

論点 3: /lgtm-loop の継続レビューをどうするか（最大の技術論点）

lgtm-loop は「1 巡目 /codex-review → 2 巡目以降 mcp__codex__codex-reply（threadId）」という契約で、 レビュアーが前巡の指摘文脈を保持したまま修正を再レビューする。プラグインには threadId に相当するプログラム的な継続 API がない （codex resume <session-id> は人間が Codex 側で開くための導線、--resume は rescue 用）。選択肢は 3 つ:

案内容評価
A 当面の本命 lgtm-loop は現状どおり MCP + threadId を使い続ける（codex-review 廃止時は 1 巡目も MCP 直叩きに変更） 変更最小・契約維持。プラグインとは独立に動く
B 試用後に再評価 REVIEW ステップを毎巡 /codex:review --background のフル再レビューに置き換える（thread 継続を捨てる） background 化と公式出力スキーマの恩恵。ただし毎巡フルレビューで usage 消費が増え、指摘の文脈も切れる
C 非推奨 1 巡目だけプラグイン、2 巡目以降 MCP threadId が取れず経路もちぐはぐ。二重メンテになる

論点 4: プラグインの Stop review gate と lgtm-loop の重複 → gate は使わない

gate は Stop フックで毎応答後に Codex レビューを走らせ、指摘があれば停止をブロックする。README 自身が 「長いループになり usage limits を急速に消費しうる」と警告しており、 Max プランのセッション上限を並行タスクと共有している現状とも、静かな自動化を好む運用方針とも相性が悪い。 明示的に起動する lgtm-loop（機能ゲート AND LGTM、リトライ上限つき）の方が制御可能。

運用ルール: /codex:setup --enable-review-gate は使わない（既定 OFF を維持）。誤って有効化すると全セッションの Stop に最大 900 秒のフックが挟まる。

論点 5: トリガーと名前空間の衝突

プラグインのコマンドは codex: 名前空間かつ自動発火しないため、/codex-review と機械的な衝突はない。 問題は人間側の混乱（/codex-review と /codex:review の併存）と、自然文トリガー （「Codex にレビューして」「セカンドオピニオン」）の行き先が自作スキルにしか向かないこと。 自作 codex-review を廃止する場合、この自然文の受け皿が消えるので、 description だけ残した薄い誘導スキル（本体は「/codex:review を案内 or 実行する」1 行）に縮退させるか、 CLAUDE.md に誘導を 1 行書く。プラグイン同梱の補助スキル（codex-cli-runtime / codex-result-handling / gpt-5-4-prompting）は Codex CLI 話題でのみ発火する補助で、既存スキルとの競合は実質ない。

論点 6: モデル設定の単一ソース原則 → 維持どころか強化される

プラグインも MCP も同じ ~/.codex/config.toml（model = "gpt-5.6-sol"）を継承するため、 「config.toml の 1 箇所だけ更新すればよい」という現行原則はそのまま両経路に効く。 ついでに直すべき既存の記載ずれを発見: 自作 3 スキルの SKILL.md は model_reasoning_effort = max と書いているが、実際の config.toml は xhigh。統合作業のついでに修正する。 なお web_search = "live" はレビュー（読み取り専用）には影響せず、rescue でタスク委譲する際に生きる。

論点 7: 配布と新ホスト再現性（nanokit への組み込み）

プラグインの実体は ~/.claude/plugins/ 配下の state で、scrapling / workspace MCP の user スコープ登録と同じ 「dotter 管理外・ホストごとに登録が要る」カテゴリに入る。./nanokit codex-install（codex_mcp_register の隣）に marketplace 追加とインストールを冪等に足すのが素直: 

claude plugin marketplace add openai/codex-plugin-cc
claude plugin install codex@openai-codex
未確認 2 点: (1) claude plugin の非対話 CLI での正確な引数（上記はドキュメント上のスラッシュコマンド /plugin ... の CLI 相当。実装時に claude plugin --help で確認）。 (2) HDT の隔離設定（CLAUDE_CONFIG_DIR=~/.claude-hdt）にプラグイン state が波及するか。おそらく config dir ごとに別インストールが必要で、claude-settings 側の setup 手順にも追記が要る。

依存の Node ≥ 18.18 は codex 本体を npm で入れている既存例外の範囲内（v22.22.3 あり）で、pixi-only 方針への新たな逸脱はない。 プラグイン更新で hooks / 挙動が変わるリスクは、rtk と同じ「バージョンアップ時に diff を確認して取り込む」運用でカバーする。

5. 移行ステップ案

Phaseやることゲート（次に進む条件）
0. 併走試用
即日・可逆		 marketplace 追加 → /plugin install codex@openai-codex → /codex:setup。review gate は OFF のまま。自作スキルは温存し、レビューだけ /codex:review --background を数回使ってみる レビュー品質・所要時間・usage 消費が自作経路と同等以上
1. レビュー移行 レビュー用途を /codex:review / /codex:adversarial-review に一本化。自作 codex-review は薄い誘導スキルに縮退（or 削除 + CLAUDE.md に誘導 1 行）。SKILL.md の effort 記載ずれ（max → xhigh）修正 自然文トリガー（「GPT にレビューして」）が迷子にならない
2. lgtm-loop 再設計判断 案 A（MCP 維持、1 巡目を MCP 直叩き化）を実装。Phase 0-1 の試用感で案 B（毎巡フルレビュー + background）へ進むか判断 ループ 1 周の実測（時間・usage）が許容内
3. nanokit 組み込み ./nanokit codex-install にプラグイン登録を冪等追加、CLAUDE.md（新ホスト手順・Codex 運用節）更新、HDT config dir への波及を検証して claude-settings 側にも追記 新ホストで ./nanokit install → codex-install だけで再現
撤退条件: Phase 0 でレビュー品質が自作プロンプトより明確に劣る、または background ジョブ管理が不安定なら、プラグインは rescue / transfer 専用に格下げし、レビューは現状維持。プラグインのアンインストールだけで完全に元に戻る。
